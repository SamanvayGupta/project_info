01

What does this project do?

The user-facing goal and the practical problem it addresses.

OBSERVE

See system health

Displays system-level CPU and memory information, plus performance trends such as disk and network activity where implemented.

INSPECT

Understand individual processes

Lists running processes with details such as process ID, name, CPU use, memory use, state and thread count where available.

INVESTIGATE

Spot potential issues

Uses simple thresholds such as CPU ≥ 25% or RSS ≥ 500 MB to flag processes for closer inspection. A flag is a hint, not proof of a fault.

ACT

Manage processes

Provides actions such as suspend, resume and terminate, subject to operating-system permissions and confirmation/error handling.

Scope note: This is a monitoring and management dashboard, not a replacement for the operating-system scheduler. It observes information exposed by the OS and requests process-control actions through supported APIs.

  1. Start the app. The entry point creates the Qt application and shows the main dashboard window.
  2. Start monitoring. A background monitor periodically collects system and process metrics to keep sampling work out of the main UI path.
  3. Prepare the data. Process information is converted into values for the table, metric cards and graphs. Disappearing processes and restricted metrics need error handling.
  4. Refresh the screen. The UI updates summary cards, process rows and rolling chart history. A graph usually retains a bounded window of samples.
  5. Interact. Search and state filters narrow the list. Selecting a process can reveal details; process-control actions ask the OS to change that process.
  6. Repeat. The next sampling cycle updates the display, making changes visible over time.

main.py

Entry point

Gives the user a simple file to run. Startup stays separate from UI and monitoring logic.

process_dashboard/app.py

Application bootstrap

Creates the Qt application object, configures startup, constructs the dashboard and starts the event loop. The event loop handles input, painting, timers and queued signals.

process_dashboard/dashboard.py

Interface coordinator

Builds the main window and pages, connects buttons and filters, receives monitor updates, and tells cards, graphs and the process table what to display.

process_dashboard/monitor.py

Data collection

Uses psutil to query OS metrics periodically. A worker thread helps keep slower sampling from freezing the UI. Results should be passed to widgets safely using Qt signals.

process_dashboard/table_model.py

Table data adapter

Implements Qt's model/view contract so the process table can request row count, column count and cell values. This separates data from appearance.

process_dashboard/widgets.py

Reusable visuals

Holds repeatable widgets such as metric cards and live graphs. Reuse avoids duplicating layout and chart-update logic.

process_dashboard/theme.py

Visual consistency

Centralizes colors and widget styling, allowing appearance changes without mixing style rules into monitoring logic.

process_dashboard/config.py

Shared settings/helpers

Holds common configuration values and helpers such as readable byte formatting, depending on the exact implementation.

tests/test_config.py

Regression checks

Runs automated assertions for helper behavior it covers. It does not prove the GUI, process actions or every operating system work correctly.

requirements.txt

Environment setup

Lists third-party dependencies so another machine can install them using pip.

launch.bat

Windows convenience

Can launch the app from Windows, depending on its contents and Python environment configuration.

Why modularize? Each file has one main responsibility. That makes bugs easier to locate, widgets reusable, and individual helpers easier to test.
04

The logic behind key features

Concepts to understand—not just the file names.

CPU usage: why sampling matters

CPU utilization is a rate over time, not just a single counter. psutil may need a baseline call and a later call to calculate usage over an interval. The first reading can be a warm-up. Per-process CPU may exceed 100% when a process uses multiple cores, depending on the metric definition.

Memory usage: what is measured?

Process memory commonly uses resident set size (RSS): physical memory currently resident for that process. RSS is not the same as all memory allocated, and shared pages complicate comparisons. System memory percentage and a process's RSS are different measures.

Process states and disappearing processes

The OS can create or end processes between refreshes. Access may be denied for protected processes. Queries should handle a process disappearing, access being denied, or a zombie state on systems that expose it; one failed query should not crash the dashboard.

Background monitoring and Qt threading

A periodic worker helps keep sampling from monopolizing the GUI thread. Qt widgets should normally be changed on the GUI thread; worker results should be delivered through signals/slots or another safe queued mechanism. Faster polling feels more live but can increase overhead.

Charts and bounded history

A live graph adds each sample and discards old points beyond a configured maximum (the described version keeps around 60 points). This shows a short trend without allowing history to grow forever.

Issue flags and thresholds

Rules such as CPU ≥ 25% or RSS ≥ 500 MB are simple heuristics. A busy application may be behaving normally, so flags should be treated as prompts for investigation, not proof of a fault.

Suspend, resume and terminate

These actions request changes through process APIs; they can fail due to permissions, OS policy, protected processes or race conditions. Confirm disruptive operations, validate selection, catch errors and refresh afterward. Terminating a critical process can cause data loss or instability.

Why use a table model?

Qt's model/view design separates the data source from the visual table. A model supplies values and roles; a view decides how to show them. This is easier to extend with sorting, filtering and formatting than embedding all logic in UI construction.

07

Limitations and responsible use

Understanding what the project does not promise is important.

Permissions

Some processes cannot be inspected or controlled without elevated privileges. Do not elevate privileges unless needed and understood.

Platform differences

Windows, Linux and macOS expose different process states, counters and controls. Validate the target OS explicitly.

Sampling overhead

Frequent polling and rebuilding large tables can add overhead. Tune the interval and update only what changed where practical.

Heuristic warnings

High CPU or memory does not necessarily mean a problem. Future versions could offer configurable thresholds and time-based alerts.

Testing coverage

The current test file covers only its written assertions. GUI and safe process-action testing should be recorded separately.

Security and safety

Terminating a process can lose work. Validate inputs, ask for confirmation, handle errors and avoid exposing sensitive details unnecessarily.

08

Viva practice

Use these prompts to test your understanding in your own words.

1. Why did you use psutil?

It provides APIs for process enumeration, CPU and memory statistics, disk/network counters and supported process actions, avoiding much low-level OS code.

2. Why separate monitoring from the dashboard?

Sampling can take time; a worker helps keep the interface responsive, clarifies responsibilities and makes monitoring easier to test. UI changes must be delivered safely to the GUI thread.

3. What is the difference between system memory and process RSS?

System memory summarizes machine-wide use; RSS estimates physical memory resident for one process. They measure different scopes.

4. How do you decide a process is problematic?

This version uses high CPU/memory thresholds as heuristics. They are signals for investigation, not proof; thresholds depend on workload.

5. What if a process exits during a query?

Catch per-process exceptions, skip or mark unavailable data, and keep the overall monitor running.

6. What does pytest prove?

It verifies assertions actually in the test suite. It does not prove the whole GUI works; platform behavior needs additional testing.

7. How does the project satisfy the assignment?

It visualizes process state, CPU and memory; refreshes keep information timely; filters and process controls support management; charts and thresholds help surface possible issues. Demonstrate each feature in the running app.

Preparation tip: Be ready to trace one feature from its UI control to the handler, then to the monitoring/library call, and back to the refreshed display. Explain only what you have personally verified.
